# Current Feature

**Type:** Fix
**Branch:** fix/carousel-shared-layout
**Status:** verified

## Goal

Carousel: one shared set of layout options for the whole block, not a separate set per slide.

## The problem

Since build step 12 of the Carousel feature (`blueprint/history/features/33c-carousel.md`), every slide in [config.ts](src/blocks/Carousel/config.ts) carries its own full Layout tab - **Type** (Text-only/Split/Media Background), **Surface**, **Text position**, **Text alignment**, **Media fill**, **Overlay coverage/color/opacity** - independently of every other slide. A carousel can end up with slide 1 as Split, slide 2 as Media Background, slide 3 as Text-only, each with its own alignment/overlay choices. The user wants one shared layout for the whole carousel instead: set it once, every slide uses it.

## The fix

Hoist the Layout tab's fields from each slide (`items.<n>`) up to the Carousel block's own existing Layout tab, alongside `transition`/`width`/`autoplay`/`autoplayInterval`. The Content tab keeps everything genuinely per-slide: `heading`, `subheading`, `mediaType`, `image`, `video`, `videoLoop`/`videoHideControls`, `links`.

`mediaType`/`image`/`video`'s `admin.condition` currently reads the slide's own `siblingData.layout`. Once `layout` moves up a level, those conditions switch to Payload's third condition argument, `blockData` (the nearest parent block's data), which already resolves correctly for a field nested inside the block's `items` array - see [Payload's `Condition` type](node_modules/payload/dist/fields/config/types.d.ts) for the exact signature.

In [Component.tsx](src/blocks/Carousel/Component.tsx), `Carousel` reads the shared fields from its own props and passes the same values to every `CarouselSlide`, instead of each slide reading `item.layout` etc. The outer `<Section>`'s `surface`/`hasBackgroundImage`/`splitMediaSide`/`hasDarkOverlayText` props simplify: the layout "mode" itself is now the same regardless of which slide is active, so only whether the *active slide's own media* (image/video) is actually set still needs per-slide recomputation.

The home page's live Carousel block currently has per-slide layout values (possibly different per slide already). Migrate it rather than let it go stale: take slide 0's current layout settings as the new shared block-level values, and strip the old per-slide layout keys from every item.

## Addition: vertical text alignment

User-requested addition on top of the shared-layout work above, scoped to Carousel only (not Hero). A new shared `verticalAlign` field (Top/Center/Bottom, default Center) controls where the whole text content block sits vertically, in every layout mode:

- **Split:** the row's cross-axis alignment (text column vs. media column) at `atMedium` width - currently hardcoded to `atMedium:items-center` unless `mediaFill` is Stretch, which keeps forcing `atMedium:items-stretch` regardless (Stretch already means "match the media's height," so vertical alignment has nothing left to control there).
- **Text-only / Media Background (and Split + Media fill: Full-bleed, which renders the text column alone in its own flex-col box):** currently the vertical position is accidentally coupled to the *horizontal* `align` field (`justify-end` only when `align` is Right, `justify-center` otherwise) - a pre-existing quirk, not something previously configurable on purpose. `verticalAlign` replaces that coupling outright and becomes the one thing driving `justify-*` there.

      - **Bug 1, caught after first reporting "done," not before:** the first version built both Tailwind class names by template-literal interpolation (`` `atMedium:items-${verticalAlignClass}` ``, `` `justify-${verticalAlignClass}` ``). Tailwind's scanner only emits a class it finds as a complete literal string in source - `Stack.tsx` documents this exact pitfall in its own comment, and this change violated it. `atMedium:items-start`/`atMedium:items-end` had no literal occurrence anywhere in the codebase, so no CSS rule existed for either - Top/Bottom silently did nothing in Split layout while the field itself looked wired up correctly in tests (which only assert the className string, not real CSS). `justify-start`/`justify-end` happened to still render, coincidentally, because `Stack.tsx` already uses those exact literal strings elsewhere. Fixed by replacing both interpolations with explicit `VERTICAL_ALIGN_JUSTIFY`/`VERTICAL_ALIGN_ITEMS` literal lookup maps (`Component.tsx`, module scope), mirroring `Stack.tsx`'s own `GAP`/`ALIGN`/`JUSTIFY` maps. Confirmed by running a real `next build --experimental-build-mode generate` (compile mode alone doesn't emit the CSS bundle) and grepping the output for `.atMedium\:items-start`/`.atMedium\:items-end` - both present after the fix, absent before it.
      - **Bug 2, reported as "still not working" / "not at all" after Bug 1's fix, found by fetching the real running dev server's rendered HTML directly (`curl`) rather than guessing further:** `textContentClassName` applied `'flex-1'` to the text Stack unconditionally. That's correct inside the row layout (Split, not Full-bleed) - it shares the row's horizontal space with the media column - but in every other case (Text-only, Media Background, Split + Full-bleed) the content div is `flex-col`, where `flex-1` stretches the Stack to the content div's own full height along the *vertical* main axis instead, leaving `justify-*` no spare space to redistribute. This bug predates this fix entirely (it's why the old, accidental `contentAlign`-driven `justify-end` case - horizontal align: Right - was equally inert before `verticalAlign` existed; nobody had reported it because that specific combination was never checked). Fixed by gating `'flex-1'` on a new `isRowLayout` (`hasSideMedia && mediaFillMode !== 'fullBleed'`) boolean, which also replaced the same inline condition repeated twice elsewhere in the same render. Live-verified against the actual running dev server (confirmed via direct `curl` of the rendered page, before and after) - not just reasoned about.
      - Added a regression test asserting the text Stack never carries `flex-1` outside the row layout.
      - **Bug 3, reported as "does not work when stretch is selected":** Media fill: Stretch forces the row's own `atMedium:items-stretch` (overriding `VERTICAL_ALIGN_ITEMS` entirely, by design - see the step's own note on why), which stretches the text column's *wrapper* to the row's full height. That wrapper is a `<Stack>`, and Stack's own default `justify` prop ('start') then pinned the heading/subheading/buttons group to the top of that now-tall wrapper, regardless of `verticalAlign` - a second, narrower instance of the same "stretched box, no spare-space signal" class of bug as Bug 2, just one layer deeper (inside the Stack component itself, not the content div around it). Fixed by passing the Stack a `justify` prop too, via a third literal map (`VERTICAL_ALIGN_STACK_JUSTIFY`, mapping to Stack's own `'start' | 'center' | 'end'` prop values rather than Tailwind classes directly - Stack.tsx does its own literal-class mapping internally, so no interpolation risk here). Added a regression test for Stretch specifically.

## Addition: remove the outer section's vertical padding

User-reported: the Carousel section renders too tall. `Carousel`'s own `<Section>` reused Hero's exact `className="ui-hero-section"`, which has no purpose other than one CSS override in `_section.css` (`.ui-hero-section.ui-section[data-spacing] { --section-space: var(--hero-space); }`, specificity (0,3,0)) that pins `--section-space` to Hero's Settings-driven value regardless of what `spacing` prop is actually passed - `[data-spacing]` matches on attribute *presence*, not value, so passing `spacing="none"` alone wouldn't have escaped it. Carousel's own viewport is already a fixed `aspect-video` box, so this extra top/bottom section padding was pure added height the block doesn't need. Fixed by dropping `className="ui-hero-section"` entirely (confirmed via grep it has no other consumer) and passing `spacing="none"` instead, which now resolves through the generic, unoverridden `.ui-section[data-spacing='none'] { --section-space: 0rem; }` rule. Live-verified via `curl` against the real rendered page: the carousel's `<section>` now reports `data-spacing="none"` with no `ui-hero-section` class, vs. the other blocks' `data-spacing="normal"`/`"tight"`.
