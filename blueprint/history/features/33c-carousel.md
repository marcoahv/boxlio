# Current Feature

**Branch:** feature/carousel
**Status:** verified

## Goal

Add **Carousel** (build plan 33c) to the shared block registry (`src/blocks/registry.ts`): a client-interactive slider block with Previous/Next controls, keyboard navigation, and optional autoplay. The build plan deliberately kept Carousel out of 33a/33b because its moving viewport — only one slide visible at a time — breaks something every other registry block gets for free: the admin's hover-sync scroll-to-field (`admin-field-focus` in [useBlockSyncListener.ts](src/utilities/useBlockSyncListener.ts)) can't find or usefully scroll to a slide that isn't the active one, so a non-active slide's caption is unreachable from the sidebar.

> **Revision, caught in live Live Preview testing after the initial implementation:** the first version resolved this by stacking every slide whenever inline editing was active, mirroring `Accordion`'s "expand every panel while editing" rule. That was the wrong transfer of that precedent - `useIsEditableField()` is true for the *entire time* Live Preview is open, not just while a field has focus, so the carousel rendered as a permanent column of images any time an editor merely opened the preview, not only while actively editing a caption. Live-verified broken by the user. Fixed instead by listening for the `admin-field-focus` message directly inside the Carousel component and jumping `activeIndex` to the focused slide - the viewport behaves like a real carousel at all times, in and out of Live Preview, and a non-active slide becomes reachable only at the moment its caption is actually focused in the sidebar. See the corrected step 4 and Notes for the AI below.

## Out of scope

- Dot/thumbnail pagination indicators and touch/swipe gestures — the build plan line names only "keyboard nav, optional autoplay"; adding either would be scope not asked for.
- A visible pause/play button — pause-on-hover/focus plus the reduced-motion cutout is the minimal safe autoplay contract; a dedicated control is a bigger UI decision the build plan doesn't ask for.
- Any change to `block-hover-sync`, `useBlockSyncListener`, `blockSyncMessages.ts`, or the `useEditableField`/`EditableFieldContext` mechanism itself — the fix adds one new *listener* for the existing `admin-field-focus` message type entirely inside the Carousel component; no shared file or message shape changes.
- Inline editing inside a Lexical-embedded Carousel (`Posts.body`) beyond whatever the registry already provides project-wide — 29a already excludes rich-text bodies from inline text editing for every block, not just this one; Carousel inherits that unchanged.
- Automated e2e coverage of autoplay/reduced-motion timing — `tests/e2e/` has no existing convention for creating a throwaway Page with specific block content inside a test (the one existing spec, `theme-toggle.spec.ts`, only visits `/` and checks global header behavior), and building that fixture infrastructure for one block's timer is disproportionate. Verified manually instead (see Testing).

- [x] 8. **Fix: the Background Image overlay was blocking clicks on the Previous/Next buttons**
      - First real bug report from actually trying step 6/7 in the browser. Root cause: `.ui-carousel-overlay-text` (the centered caption, `z-index: 2`) is nested inside the slide's own `role="group"` div, which has no explicit z-index of its own and so never establishes its own stacking context. Per CSS stacking rules, a positive z-index on a descendant "leaks" past a non-stacking-context ancestor and gets compared against *every* other element in the nearest real stacking context above it - here, that's the shared `viewport` region, where the Previous/Next buttons sit at `z-index: auto`. A positive explicit z-index always outranks `auto`, regardless of DOM order, so the overlay-text's full-`inset-0` hit area painted (and captured clicks) above the buttons despite coming earlier in the DOM and being nested deeper.
      - Fixed by adding `isolate` (`isolation: isolate`) to each slide's outer `role="group"` div in both layout branches - this forces that div to establish its own stacking context with no CSS changes elsewhere, containing the caption's `z-index: 2` to just that slide so it can never compete with anything outside it again. Applied to the `boxed` branch too defensively, even though its bottom-bar caption doesn't currently overlap the buttons spatially - nothing should rely on that staying true.
      - No new automated test: jsdom doesn't implement real layout, paint order, or hit-testing, so there's no way to write a test here that would actually catch a stacking-context regression like this one - it can only be caught by looking at the rendered page. Noting that explicitly rather than claiming coverage that doesn't exist.

## Notes for the AI

- Follow `registry.ts`'s own "to add a block" comment exactly: config + component, then both maps. Nothing else should need to change for registration itself.
- Carousel becomes embeddable in `Posts.body` automatically because it's a registry block — do not special-case it out of the Lexical `BlocksFeature` list; that would contradict the registry's own "hard contract" lock in the project overview.
- `useIsEditableField()` is a page-wide flag (`src/utilities/EditableFieldContext.tsx`), true whenever Live Preview's inline-editing mode is active for the page at all — not scoped to whichever field currently has focus. That's a fine basis for `Accordion`'s "expand every panel while editing" (a FAQ list reads fine fully expanded), but it is **not** safe to reuse for any behavior whose normal, non-editing appearance *is* the feature - this bit Carousel twice: once for the viewport itself (step 4's reverted stacking override), and again for autoplay (step 5 - it was gated on the same flag and so silently never ran in Live Preview at all). The lesson: before gating ANY behavior on this flag, check whether the gated thing is the block's defining visual/behavioral trait rather than an incidental one - if it is, don't key it off "Live Preview is merely open."
- Carousel's reachability fix is a targeted `message` listener for `admin-field-focus` (already defined in `blockSyncMessages.ts`, already sent by `block-hover-sync/Component.tsx` whenever a field gets focus in the admin sidebar) - filter on `message.blockId === id` and a `fieldPath` matching `items.<n>.` (broadened from a literal `.caption` suffix in step 12, since every slide now has many editable fields, not one), then move the active slide to `n` (via `moveActive`, step 11 - was a bare `setActiveIndex(n)` before that). A future block with the same "moving/hiding content" shape should reach for this pattern - react to the specific focus event, not a blanket response to the page-wide editing flag.
- A mouse click that leaves a button focused, with no later `blur`, can permanently stick an `onFocus`-driven boolean `true` if nothing else ever takes focus afterward - this is what happened to autoplay's `isPaused` state via the Previous/Next buttons. `onMouseDown={(event) => event.preventDefault()}` on the button is the standard fix (stops the browser's default mouse-click-focuses-this-element behavior without affecting keyboard Tab+Enter/Space activation at all). Worth checking for on any other focus-driven boolean state in this project.
- jsdom (this project's Vitest `environment`) does not implement `window.matchMedia` at all - any test that exercises code calling it (this block's reduced-motion check, `ThemeToggle.tsx`'s dark-mode detection) needs a local stub or it throws. None of the pre-existing tests had hit this before Carousel's autoplay tests needed one.
- Before giving a block its own `Container` `width` prop, check `_section.css` first: `.ui-section-container.ui-container[data-width]` (and the equivalent `ui-hero-container`/`ui-rich-text-container` rules) match on attribute *presence*, not value, and win by specificity over the generic per-value rules - so every block routed through one of those classes has its `width` prop silently pinned to one sitewide Settings token no matter what value is actually passed. Only `Header` (via plain `ui-container`, no wrapper class) and now `Carousel` (via its own `ui-carousel-container` + explicit per-value rules, see step 6) have a `width` that actually does anything. This would have shipped as a silent no-op field without reading that file first.
- A descendant's explicit `z-index` only stays contained to its own layer if an ANCESTOR actually establishes a stacking context (a numeric `z-index` + non-static `position`, or `isolation: isolate`, or a few other triggers - plain `position: relative`/`absolute` alone does *not*). If nothing between a `z-index`-ed element and some unrelated sibling establishes one, that z-index "leaks" and gets compared directly against the sibling's own stacking level instead - this is what let the Background Image overlay's `z-index: 2` caption block the Previous/Next buttons' `z-index: auto` in step 8, despite the buttons being later in the DOM. Any full-coverage (`inset-0`) overlay sitting near other interactive controls should get `isolate` on its own containing element as a matter of course, not just when something breaks.
- **Slide transition's direction convention (step 10), in case it needs reversing:** Next (right) brings the new slide in from the right, track moves left; Previous (left) brings it in from the left, track moves right - the universal carousel-library convention, picked over the literal (and ambiguous) request wording without asking first. To flip it, negate the sign in `slideOffset()` (`slideIndex.ts`) - `CarouselSlide`/`_carousel.css` just consume whatever sign it returns and don't encode the convention themselves.
- **This project's ESLint config enforces `react-hooks/refs` (React Compiler-era rules): reading `ref.current` during render is a hard lint error, not just writing it** - confirmed the hard way in step 11, where a `useRef`-based "remember the previous offset" approach failed lint outright. Nothing else in this feature (or apparently this codebase generally) had exercised that rule before. The fix pattern that IS allowed: fold the "needs the previous value" logic into a `setState` functional updater instead, where the previous value arrives as a plain parameter (not a ref read) - see `moveActive`'s own `setActive((current) => ...)` in `Component.tsx`. Reach for this pattern first, before a ref, whenever a render needs to compare against "what was true last time."
- **A circular "shortest path to the current active index," recomputed fresh every render, is not safe to animate directly** - for a slide not involved in the current step, its own shortest side can flip relative to its PREVIOUS value even though it didn't move far at all conceptually (step 11's bug). The general fix - compare the new per-slide value against what it was before the state actually changes (inside the same state transition, not a separate read), and render any change bigger than one legitimate "step" instantly rather than animated - generalizes beyond this block to anything else that positions multiple items via a circular/wrapping distance function and transitions that position with CSS.
- **Before guessing which fields a "give it the options of X" request means, especially when X has sub-items and the request's own block doesn't (or vice versa), ask which axis is shared vs. per-item** - this feature asked once (step 12's own question), got "shared," and the user then explicitly reversed that to "every slide gets all the options" before any code existed yet. Cheap to ask, expensive to guess wrong once a large rewrite is underway - the question itself is reusable practically verbatim for a future "make block A work like block B" request.
- **Hero's own file (`src/blocks/Hero/config.ts`/`Component.tsx`) is intentionally untouched by step 12, even though its field set and render logic are now duplicated (not shared) inside Carousel.** This was a deliberate choice under time/risk pressure, not an oversight - extracting Hero's content into something both blocks call would be the more maintainable long-term shape, but risked regressing a shipped, independent block in the same pass as this large a Carousel rewrite. If Hero's own layout/overlay logic changes later, Carousel's `CarouselSlide` needs the same change ported by hand - there is no shared source of truth today.
